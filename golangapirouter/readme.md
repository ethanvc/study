# 概述
在软件系统中，为了屏蔽单点故障，尝尝需要有一定的冗余措施。为了实现机房冗余，设计了如下的请求路由方案。该方案一般应用到系统中名为gateway的服务中。
由于机房存在搬迁、裁撤的需求，抽象出一个单元的概念，单元对应一组服务，部署在同一个机房，每一个请求路由到合适的单元进行处理。
当单元所在的机房需要切换时，将流量全部切到其它单元，然后执行机房搬迁逻辑，完成之后，切回流量即可。

# 行业调研
1. 同城多活：数据中心距离近（通常<100km），网络延迟低（毫秒级），可实现数据强一致性或最终一致性，RTO/RTO目标极低。
2. 异地多活：数据中心距离远（>300km），可应对城市级灾难。网络延迟较高，通常采用数据最终一致性和单元化架构。
3. 混合云/多云多活：结合公有云和私有云，提供部署灵活性、成本优化和避免云服务商锁定。
4. 多活数据库架构：核心在于解决数据在多副本下的读写一致性和同步性能问题，是任何多活方案的基石。

# 需求分析
**多活的本质是解决数据的可用性问题**。
数据的可用性归纳为解决如下问题：
1. 不能容忍数据不一致的，只能去主所在的地方处理。
2. 可以容忍数据不一致的，优先就近处理。
3. 有损容忍数据不一致的，优先去主所在的地方处理。
4. 为了降低数据不一致带来的负面影响，可以通过各种缓存处理措施，加快数据一致性进度。

接口分为有状态和无状态接口，对于有状态的接口，需要按依赖的数据在哪些单元进行路由。路由的核心是数据归属。

当gateway收到一个请求之后，需要判断，该请求应该转发到后端哪一个单元，存在如下场景：
1. fix：请求需要指定的单元进行处理，且gateway能够判断具体的单元编号。
2. any：请求在任一单元可以处理。
3. try：请求需要指定的单元进行处理，但是gateway无法轻易判断是哪个单元，因此需要先尝试请求一次，根据后端的返回，判断是否已经处理，或者是后端提供了正确的处理单元编号。

对于不支持单元化的服务，可能有类似主备服务，api需要根据特性路由到主服务还是备服务。一般写接口和要求数据一致性的接口需要路由到主服务，否则路由到备服务也能处理。

任何一个api的路由，最终都可以分类到上述三种场景。以下举例说明。

## 无状态接口
如果请求无状态，或者是容忍缓存不一致，任一单元都可以处理该请求，则属于any路由方式。gateway采用一定的策略选择一个单元即可处理请求。
## 收单
收单存在两种场景：
1. 新请求：此时，任一单元都可以处理该请求，属于any路由方式。
2. 重试请求：此时，需要和第一次路由保持同样的单元，属于fix路由方式。

## 查单，知道单元编号
属于fix路由方式。

## 查单，不知道单元编号
属于try路由方式。

## 获取订单列表
请求需要聚合所有单元的数据，然后返回。属于any路由方式，接口收到请求之后，自行请求其它单元获取所有数据合并返回。

# 方案设计
1. 单元化的本质是数据的单元化。路由的核心是请求和数据的绑定。
2. 根据阿里的MSHA里提到的，抽象逻辑数据中心，成为一个单元。逻辑数据中心一般映射到一个机房。

## Action
Action封装了一个动作，该动作对输入进行处理，并产生一些输出。

## 表达式
要关注数据类型，重点关注数字、字符串、数组，函数对这些类型的处理可能不符合用户的预期。

## 变量
1. 需要可以引用body的整个内容，而不是取某一个key的值。

## 如何选择单元
有三种方式：
1. 随机数。太灵活了，不好，除非是无状态接口，否则不建议使用。
2. 单号。流量更加均匀，更受控。
3. 用户ID。用户单热点问题，用户可能不是自然人，同一个账号出现大量订单，无发在单元间进行有效分布。
   1. 优点是，系统的缓存一致性会比较好。

结论：有单号选单号，没单号选用户ID，最后选随机数。

## 扩展到任意多个单元的瓶颈？如何解决。
1. 如果能够在1-2次确定单元，就可以接受。
2. 一个请求不能依赖所有单元才能完成。

## 距离的影响
- 300km 是 “抗灾有效性” 的最低门槛。收、地理、城市、行政区域决定。可能跟城市+自然灾害大小限制有关系。
- 300km 是 “数据同步延迟” 的可控上限。光纤中信号传播速度约 200km/ms。延时太大会影响分布式事务的成功率和放大数据不一致的影响。

## 流量调度
我们会设计一个全局流量调度功能，为了提高性能，不能每个api都去执行这个调度规则。
可以这样实现： 有一个静态匹配规则，只能引用rule的变量，这个可以提前计算，只有满足规则的api，后续才要执行流量调度规则。
同样，流量调度规则影响的api列表，可以提前知道，避免不符合预期。
