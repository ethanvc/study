## 总览
1. 加锁之后，事务结束，琐一起释放。
2. 幻读：指的是在一个事务内，同一个查询​ 在执行两次（或多次）时，由于其他并发事务的插入操作，
导致第二次查询返回了之前不存在的额外行（这些新行就像“幻影”一样突然出现）。

## 间隙锁
间隙锁是 InnoDB 在可重复读（RR）隔离级别下为解决幻读引入的锁类型，
它锁定的是索引记录之间的空白区间（间隙），而非记录本身；
且间隙锁的范围完全由查询所使用的索引类型（主键 / 唯一索引、普通索引、复合索引）
和查询条件类型（等值、范围）决定，与数据的物理存储位置无关（仅依赖索引的 B + 树有序性）。


本质是对索引键值的一个左开右闭区间进行锁定。

你希望我详细讲解MySQL InnoDB存储引擎中的**Next-Key Lock（临键锁）**，包括它的本质、作用机制、不同场景下的行为以及与间隙锁、
记录锁的关联，这是理解InnoDB解决幻读问题的核心知识点。

首先需要明确：Next-Key Lock是InnoDB在**可重复读（RR）**隔离级别下的**默认锁机制**，它是**记录锁（Record Lock）**和**间隙锁（Gap Lock）**
的组合体，本质是对**索引键值的一个左开右闭区间**进行锁定。其核心目的是解决可重复读级别下的**幻读问题**，同时兼顾数据的并发访问控制。

---

## 一、前置基础：理解Next-Key Lock的组成部分
在讲解Next-Key Lock之前，必须先掌握其两个基础锁类型，这是理解临键锁的前提：

### 1. 记录锁（Record Lock）
- **定义**：锁定**索引记录本身**的锁，仅作用于**存在的索引键值**。
- **作用**：防止其他事务对该记录进行更新或删除。
- **示例**：对主键`id=2`的记录加记录锁，其他事务无法修改或删除`id=2`的行。

### 2. 间隙锁（Gap Lock）
- **定义**：锁定**两个索引记录之间的空白区间**（间隙），或第一条记录之前/最后一条记录之后的区间，不锁定记录本身。
- **作用**：防止其他事务在该间隙中插入新记录，从根源上避免幻读。
- **示例**：主键`id`的记录为`1,3,5`，则间隙包括`(-∞,1)`、`(1,3)`、`(3,5)`、`(5,+∞)`，对`(1,3)`加间隙锁后，其他事务无法插入`id=2`的行。

---

## 二、Next-Key Lock的核心定义与特性
### 1. 本质定义
Next-Key Lock = **记录锁（锁定当前索引记录） + 间隙锁（锁定当前记录之前的间隙）**，它锁定的是一个**左开右闭的索引区间**：`(prev_key, current_key]`。
- `prev_key`：当前索引记录的**前一个相邻索引键值**（若没有则为`-∞`）。
- `current_key`：当前命中的索引记录的键值（若没有则为`+∞`）。

### 2. 核心特性
| 特性                | 说明                                                                 |
|---------------------|----------------------------------------------------------------------|
| **生效级别**        | 仅在**可重复读（RR）**隔离级别下生效（InnoDB默认隔离级别）；在**读已提交（RC）**级别下，间隙锁被禁用，Next-Key Lock会降级为记录锁。 |
| **索引依赖性**      | 仅作用于**查询使用的索引**（主键、唯一索引、普通索引、复合索引）；若查询未使用索引（全表扫描），会对**所有索引的所有间隙**加锁（等效表锁）。 |
| **区间锁定规则**    | 基于索引的**有序性**划分区间，与数据的物理存储位置无关。               |
| **幻读解决方案**    | 既锁定已存在的记录（防止修改/删除），又锁定间隙（防止插入新记录），彻底解决幻读。 |

### 3. 索引区间的划分规则
Next-Key Lock的区间划分完全依赖**当前表中已存在的索引键值**（按升序排列）。我们通过**示例表**来直观理解：
```sql
-- 创建测试表，包含主键id、普通索引idx_age
CREATE TABLE t (
    id INT PRIMARY KEY AUTO_INCREMENT,
    age INT,
    KEY idx_age (age)
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

-- 插入测试数据
INSERT INTO t (age) VALUES (20), (25), (30);
```
此时，**主键索引`id`**的键值为`1,2,3`，对应的Next-Key区间为：
1. `(-∞, 1]`：第一条记录的区间（间隙`(-∞,1)` + 记录`1`）
2. `(1, 2]`：第二条记录的区间（间隙`(1,2)` + 记录`2`）
3. `(2, 3]`：第三条记录的区间（间隙`(2,3)` + 记录`3`）
4. `(3, +∞)`：最后一条记录之后的区间（仅间隙，无记录锁）

**普通索引`idx_age`**的键值为`20,25,30`，对应的Next-Key区间为：
1. `(-∞, 20]`
2. `(20, 25]`
3. `(25, 30]`
4. `(30, +∞)`

> 注意：最后一个区间`(max_key, +∞)`只有间隙锁，没有记录锁（因为没有对应的索引记录）。

## 三、不同场景下的Next-Key Lock行为（核心重点）
Next-Key Lock并非始终保持“记录锁+间隙锁”的完整形态，会根据**索引类型**（主键/唯一索引 vs 普通索引）和**查询条件类型**（等值 vs 范围）发生**降级**或**范围扩展**。以下结合示例表`t`的场景逐一说明：

### 场景1：主键/唯一索引的**等值查询**
主键和唯一索引的键值具有**唯一性**，InnoDB会根据是否**命中记录**对Next-Key Lock进行降级，以提升并发性能。

#### 子场景1.1：等值查询**命中记录**
→ **Next-Key Lock降级为记录锁**（仅锁定索引记录本身，无间隙锁）。
```sql
-- 事务1：主键id=2存在，命中记录
BEGIN;
SELECT * FROM t WHERE id = 2 FOR UPDATE;
```
- 锁定范围：仅`id=2`的记录（记录锁），不锁定`(1,2)`或`(2,3)`间隙。
- 并发影响：其他事务可在`(1,2)`插入`id=1.5`（整数则`id=4`）、`(2,3)`插入`id=2.5`，无阻塞。

#### 子场景1.2：等值查询**未命中记录**
→ **Next-Key Lock降级为间隙锁**（仅锁定对应间隙，无记录锁）。
```sql
-- 事务1：主键id=4不存在，未命中记录
BEGIN;
SELECT * FROM t WHERE id = 4 FOR UPDATE;
```
- 锁定范围：仅`(3, +∞)`的间隙（间隙锁），无记录锁。
- 并发影响：其他事务无法插入`id=4`、`id=5`等，但可修改/删除`id=3`的记录。

### 场景2：普通索引的**等值查询**
普通索引允许**重复键值**，无法通过等值查询确定唯一记录，因此Next-Key Lock**不会降级**，保持完整的区间锁定。

#### 子场景2.1：等值查询**命中记录**
→ 锁定**当前记录的Next-Key区间**（记录锁+间隙锁）。
```sql
-- 事务1：普通索引age=25存在，命中记录
BEGIN;
SELECT * FROM t WHERE age = 25 FOR UPDATE;
```
- 锁定范围：`(20, 25]`区间（间隙`(20,25)` + 记录`25`）。
  > 补充：若普通索引存在重复值（如插入`age=25`的另一条记录），则会锁定**所有等值记录的区间** + 最后一个等值记录后的间隙。
- 并发影响：其他事务无法插入`age=22`（属于`(20,25)`），也无法修改/删除`age=25`的记录，但可插入`age=26`（属于`(25,30)`）。

验证方式： `mysql> select * from performance_schema.data_locks\G`

#### 子场景2.2：等值查询**未命中记录**
→ 锁定**对应的Next-Key区间（仅间隙）**，与主键未命中场景一致。
```sql
-- 事务1：普通索引age=28不存在，未命中记录
BEGIN;
SELECT * FROM t WHERE age = 28 FOR UPDATE;
```
- 锁定范围：`(25, 30)`间隙（属于`(25,30]`区间的间隙部分）。
- 并发影响：其他事务无法插入`age=28`、`age=29`，但可修改/删除`age=25`、`age=30`的记录。

### 场景3：所有索引的**范围查询**
范围查询（`>、<、>=、<=、BETWEEN`）是Next-Key Lock范围最广的场景，会锁定**所有满足范围条件的Next-Key区间**，包括范围结束后的第一个区间。

#### 子场景3.1：主键范围查询
```sql
-- 事务1：主键id>1 AND id<3
BEGIN;
SELECT * FROM t WHERE id > 1 AND id < 3 FOR UPDATE;
```
- 满足条件的记录：`id=2`。
- 锁定范围：`(1, 2]`区间（间隙`(1,2)` + 记录`2`），同时会扩展锁定`(2, 3]`的间隙部分（`(2,3)`），最终锁定`(1,3)`整个区间。
- 并发影响：其他事务无法插入`id=1.5`、`id=2.5`，也无法修改/删除`id=2`的记录。

#### 子场景3.2：普通索引范围查询
```sql
-- 事务1：普通索引age>=25 AND age<=30
BEGIN;
SELECT * FROM t WHERE age >= 25 AND age <= 30 FOR UPDATE;
```
- 满足条件的记录：`age=25`、`age=30`。
- 锁定范围：`(20,25]`、`(25,30]`区间，以及`(30, +∞)`的间隙。
- 并发影响：其他事务无法插入`age=26`、`age=35`，也无法修改/删除`age=25`、`age=30`的记录。

### 场景4：无索引的查询（全表扫描）
若查询未使用任何索引（InnoDB被迫全表扫描），则会对**所有索引的所有Next-Key区间**加锁，等效于**表级锁**，并发性能极差。
```sql
-- 事务1：查询条件为name（无索引），全表扫描
BEGIN;
SELECT * FROM t WHERE name = 'test' FOR UPDATE;
```
- 锁定范围：主键`id`和普通索引`age`的所有Next-Key区间。
- 并发影响：其他事务无法对表`t`进行任何插入、更新、删除操作，直到事务1提交。

### 场景5：复合索引的Next-Key Lock
复合索引的Next-Key区间基于**组合键值的有序性**划分（如`(a,b)`的组合值）。示例：
```sql
-- 创建复合索引表
CREATE TABLE t2 (
    a INT,
    b INT,
    KEY idx_ab (a, b)
) ENGINE=InnoDB;

-- 插入数据
INSERT INTO t2 (a, b) VALUES (1,2), (1,5), (2,3);
```
复合索引`idx_ab(a,b)`的Next-Key区间为：
1. `(-∞, (1,2)]`
2. `((1,2), (1,5)]`
3. `((1,5), (2,3)]`
4. `((2,3), +∞)`

若执行`SELECT * FROM t2 WHERE a=1 AND b=3 FOR UPDATE`（未命中记录），则锁定`((1,2), (1,5)]`区间（仅间隙`((1,2), (1,5))`）。

## 四、Next-Key Lock解决幻读的实例演示
我们通过两个事务的执行流程，直观展示Next-Key Lock如何解决幻读：
```sql
-- 环境：RR隔离级别，示例表t（id, age, idx_age），数据：(1,20),(2,25),(3,30)

-- 事务1（开启）
BEGIN;
-- 范围查询：age>=25，加Next-Key Lock
SELECT * FROM t WHERE age >= 25 FOR UPDATE;
-- 此时查询结果：id=2(25)、id=3(30)

-- 事务2（尝试插入新记录）
INSERT INTO t (age) VALUES (26); -- 被阻塞！因为age=26属于(25,30)间隙，已被事务1的Next-Key Lock锁定

-- 事务1（再次查询）
SELECT * FROM t WHERE age >= 25 FOR UPDATE; -- 结果仍为id=2(25)、id=3(30)，无幻读

-- 事务1（提交）
COMMIT;
-- 事务2的插入操作此时执行成功
```
**关键**：事务2的插入操作被Next-Key Lock的间隙锁阻塞，因此事务1两次查询的结果一致，彻底避免了幻读。

## 总结
Next-Key Lock的核心要点可归纳为以下3点：
1. **本质与作用**：它是记录锁+间隙锁的组合，锁定左开右闭的索引区间，仅在RR隔离级别下生效，核心作用是解决幻读问题。
2. **区间与降级规则**：区间划分依赖索引的有序键值；主键/唯一索引等值命中时降级为记录锁，未命中时降级为间隙锁；普通索引等值/范围查询保留完整区间锁，无索引查询等效表锁。
3. **索引依赖性**：Next-Key Lock仅作用于查询使用的索引，无索引会导致锁范围扩大（表锁），因此在高并发场景下，务必保证查询使用索引。
