在 MySQL 中，`binlog_format` 是一个核心配置参数，它决定了数据库如何将数据的变更记录到二进制日志（Binary Log）中。

MySQL 支持三种主要的格式：**STATEMENT**、**ROW** 和 **MIXED**。

---

### 1. STATEMENT (基于语句的格式)

这是 MySQL 5.1 之前的默认格式。它直接记录你执行的每一条 SQL 语句。

* **优点**：
* **日志量小**：比如一个 `UPDATE` 语句更新了 100 万行，它只记录那一行 SQL，节省磁盘和网络 I/O。
* **易于审计**：直接打开日志就能看到原始 SQL。


* **缺点**：
* **不可靠（主从不一致）**：如果 SQL 中包含“不确定性函数”（如 `UUID()`、`NOW()`、`RAND()`），主库和从库执行的结果会不同。
* **特定限制**：存储过程、触发器或复杂的 `INSERT ... SELECT` 可能会在同步时出问题。



### 2. ROW (基于行的格式)

这是从 MySQL 5.7.7 开始的默认格式，也是目前业界**最推荐**的配置。它不记录 SQL 语句，而是记录**每一行数据被修改成了什么样**。

* **优点**：
* **极致的数据一致性**：因为它记录的是最终结果，无论 SQL 包含什么复杂函数，从库拿到的都是确定的值。
* **锁的释放快**：在某些情况下可以提高并发性能。


* **缺点**：
* **日志量巨大**：如果你执行 `UPDATE t SET status=1`（影响 100 万行），日志会记录这 100 万行变更前后的完整数据，导致 Binlog 迅速撑满磁盘。
* **难以直读**：必须使用 `mysqlbinlog -v` 才能看到伪 SQL 内容。



### 3. MIXED (混合模式)

它是前两者的折中方案。

* **逻辑**：默认情况下使用 **STATEMENT** 模式，但如果 MySQL 检测到某个语句可能会导致主从不一致（例如使用了 `UUID()` 等函数），它会自动切换到 **ROW** 模式。
* **现状**：虽然看起来完美，但由于现代数据库架构对数据一致性要求极高，现在的主流实践是直接使用 **ROW**。

---

### 总结与对比

| 特性 | STATEMENT | ROW | MIXED |
| --- | --- | --- | --- |
| **日志大小** | 极小 | 较大 | 中等 |
| **一致性** | 存在风险 | **绝对可靠** | 较可靠 |
| **解析难度** | 容易 (纯文本) | 较难 (需解码) | 视情况而定 |
| **适用场景** | 简单、单机、非核心数据 | **所有高可用/生产环境** | 特殊兼容性需求 |

### 如何查看和修改？

```sql
-- 查看当前格式
SELECT @@global.binlog_format;

-- 动态修改 (需要 SUPER 权限)
SET GLOBAL binlog_format = 'ROW';

```

> **专业建议**：
> 在 2025 年的生产环境中，几乎没有理由不选择 **ROW**。配合 `binlog_row_image=MINIMAL` 参数，可以有效缓解 ROW 格式带来的日志量过大的问题（只记录被修改的列，而不是整行）。
